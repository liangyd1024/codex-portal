# Ally 列表数据库读取恢复

## 实际问题与恢复

用户截图显示 Ally 已连接，但项目及会话列表报 unable to open database file。通过 ally-ssh 技能认证连接，确认用户 ally、HOME /Users/ally、目标主机正确。首次默认 SSH 代理尝试提供过多密钥，被服务端断开；改用技能配置密码交互认证成功，未输出密码或放宽主机校验。

只读检查发现 state_5.sqlite 文件存在、可读、父目录可写、磁盘空间充足，文件头为 WAL 模式，-wal/-shm 配套文件均不存在；SQLite mode=ro 打开连接后执行查询报错。thread_history_1.sqlite 的只读查询也报同类错误。本次未修改该库。sqlite/ 子目录为既有其他数据库，与此次问题无关。

调用现有 /api/threads 的原生 thread/list（useStateDbOnly=true）后，状态库由原生引擎重新打开，出现原生创建的 -wal/-shm，项目与侧栏读取恢复。随后单独通过原生 RPC 验证 limit=1 的恢复请求成功。未改写原生数据库、全局配置、安装文件，未重启/停止目标引擎或会话。immutable=1 只读诊断可读旧数据库，但未作为修复或展示来源，避免忽略 WAL 数据。

## 代码

项目读取及 sidebar/sidebarMetadata/threads 的只读快照读取遇到指定错误时，调用已验证的原生 thread/list，再重试原读取一次。并发共享同一恢复请求，连接变更或断开后不重试；不支持原生接口、无协议验证、其他错误不触发恢复；原生失败和重试失败直接上报。服务启动/停止等操作不参与此重试流程。

## 验证

相关 Node 测试 8 项通过；完整 npm test：227 Node、53 Python 全部通过。涵盖成功恢复、持续失败、并发、连接变更、不支持/断开、原生超时及项目/侧栏接入。故障分支回归使用模拟测试，未通过删除 WAL 或改写原生数据人为复现。真实 Ally 恢复后项目接口返回 3 个项目，侧栏返回 8 个会话和 3 个项目、均无错误。未验证真实会话历史库的修复，不应将此次结果视为完整历史读取验收。
