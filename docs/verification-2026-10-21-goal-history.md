# 目标输入历史展示修复

## 原因与依据

RCM 通过 `thread/goal/set` 设置目标。该调用会自行启动原生轮次，不产生普通 `userMessage`。此前仅从 `thread_items` 读取普通消息，遗漏了用户目标输入。

已有只读桌面代码记录 `/tmp/rcm-desktop-sidebar-bundle.js` 中，`Y3t` / `J3t` 在设置目标成功后添加目标展示条目，不再次调用 `turn/start`。本次核对真实原生 rollout，确认用户显式设置目标包含 `response_item`、`content_item_kinds: ["user.goal"]`、`source="user_goal"`，随后有 `thread_goal_updated` 原生回执和目标轮次。自动继续执行的 `source="goal"` 不是新用户输入。

## 修改

- 历史读取使用原生轮次字节偏移，只读取相邻轮次之间的记录。仅在显式设置目标记录与原生回执匹配时，展示回执中的目标原文。
- 目标使用独立 `goalMessage` 展示类型，沿用黑底白字气泡并标注“目标”。不写入原生消息，不重新提交目标，不创建轮次。
- 目标更新按原生记录分别展示；自动继续、暂停和恢复不重复显示。刷新、历史分页和预览读取共用同一逻辑。
- 原生记录或字节偏移不可用时保留普通历史。旧版快照、纯协议历史回退尚不支持恢复目标输入，不宣称已覆盖。

## 验证

- `npm test`：302 项 Node、58 项 Python 测试通过。日志 `/tmp/rcm-goal-history-tests.log`。
- 新增行为回归覆盖原文和换行保留、重新读取、自动继续和恢复不重复、目标更新、历史分页、原生记录不可用，以及目标气泡不折叠进过程。
- 独立 4327 预览使用全新状态目录，未启用手机入口。通过真实只读历史恢复截图对应的目标“结合之前遇到的问题帮我进行排查”，浏览器刷新后仍显示且只有一条。
- ego-browser TaskSpace 64；桌面与 390px 页面均无横向溢出。键盘 Tab 可到达已有操作控件。目标正文没有新增交互控件，发送和输入法处理未变更；本次未执行操作系统中文输入法验收或重新发送真实目标。
- 原始会话仅用于只读展示核验，没有接管、发送、停止或修改任务。原生写入不纳入本次真实验收。
