# 网页会话引用方案补充调研

后续已按用户明确的“普通网页直接引用网页和桌面会话”需求实施只读 MCP 适配。当前实现和验证状态见[验收记录](verification-2026-10-22-web-thread-references.md)。下文保留调研当时结论。

调研基线：`ea1e306`。范围是 RCM 网页会话，不是另一套云端会话产品。只做调研和隔离探测，不修改业务功能，不部署。

## 结论

“网页创建的会话被引用”和“普通网页会话发起引用”需要分开。

| 场景 | 结论 | 证据 |
| --- | --- | --- |
| 桌面托管的会话引用网页创建的会话 | 已实现并真实通过 | 原生 `codex_app.read_thread` 返回正确随机标记 |
| 网页创建的会话作为被引用对象 | 不必交还桌面、不必打开桌面、不必自身具备读取工具 | 前一次验收是在交还源会话之前读取成功 |
| 网页 UI 操作桌面托管的发起会话 | 已有实现，依赖发起会话的原生工具能力 | `2e02eef`，正式部署另受空闲检查限制 |
| 普通网页执行通道直接发起引用 | 当前未支持 | 当前通道没有可用的桌面读取工具，RCM 也未实现动态工具处理器 |

原生真实验收见[桌面会话引用记录](verification-2026-10-22-desktop-thread-mentions.md)。仅要求“被引用”时，不需要再建会话副本、独立索引或执行引擎。

## 推荐的被引用方案

1. 从同一目标机器的原生会话目录提供候选，包含网页创建和桌面创建的会话。创建来源只是展示信息。
2. 使用连接 ID 与原生 threadId 定位会话。标题只用于展示，同名不能作为同一会话。
3. 读取能力只检查发起会话，不检查被引用会话是否具备 `read_thread`。被引用会话不必被桌面托管。
4. 选择后保存引用标识。发送前确认目标仍存在且符合可见范围，再传递标识和原生标题。
5. 桌面原生 `read_thread` 按需读取历史。保留原始工具事件和失败反馈。不能只插入标题就宣称引用成功。
6. 首期同一目标机器内引用，跨机器能力单独核验。无权限、已归档、缺失和断连时明确失败并保留草稿。

现有 `public/skill-suggestions.js` 已提供会话选择，`public/composer.js` 保留引用身份，`lib/native-automations.mjs` 校验发起者能力并解析原生标题，`scripts/desktop-session.py` 发送原生引用上下文。无需为“网页创建”的目标另设转换流程。

现有候选读取适配使用原生数据的只读目录。后续可优先使用已核验的 `thread/list`，快照回退保留来源说明；不得让展示缓存成为另一份会话依据。

## 普通网页发起引用的接口证据

官方 [App Server 文档](https://learn.chatgpt.com/docs/app-server)提供：

- `thread/read` 读取元数据，不恢复、不订阅被读取会话。
- `thread/turns/list` 和 `thread/items/list` 分页读取历史，不要求恢复会话。
- `thread/start.dynamicTools` 和 `item/tool/call` 是实验性扩展接口。工具调用通过原生轮次执行，客户端负责返回工具结果。
- 动态工具可随原生会话持久化，并在恢复时沿用。不能因此推断所有版本都支持向既有会话追加动态工具。

本机配置所指二进制为 `0.163.0-alpha.11.1`。通过原生 schema 导出核实：

- `ThreadStartParams` 有 `dynamicTools`，支持 function 和 namespace 声明。
- `ThreadResumeParams` 没有 `dynamicTools`，但有 `config`。
- `TurnStartParams` 没有动态工具注册字段。
- 原生 server request `item/tool/call` 包含发起 threadId、turnId、callId、tool 和 arguments。
- `mcpServer/tool/call` 存在，但只能调用会话已经配置的 MCP 服务，接口存在不等于桌面 `read_thread` 已接入。

隔离实测使用独立 stdio app-server 和明确的 RCM 调研客户端身份：

```json
{
  "sourceMetadataReadable": true,
  "nativeHistoryMarkerMatched": true,
  "loadedBefore": 0,
  "loadedAfterRead": 0,
  "dynamicToolsAccepted": true,
  "probeEphemeral": true,
  "modelTurnsSent": 0
}
```

读取对象仅是前次验收留下的测试源会话。工具声明仅注册在无模型轮次的临时会话。探测后退出本次独立进程，没有重启正式引擎、接管业务会话或改写全局配置。实测证明读取接口和工具声明入口可用，不证明自有工具端到端可用。

## 扩展方向比较

### 方向一：继续沿用桌面原生工具

发起会话交还后，由桌面实际打开，RCM 确认 owner 和原生工具能力，再通过既有 follower 通道发送。它最符合当前原生能力优先规则。限制是依赖桌面；“交还成功”不能等同“已获得工具”。网页来源会话转为发起者的完整路径仍待真实验证。

若未来有公开、可认证的桌面 MCP 接入或创建接口，可继续接入。当前没有核实第三方普通 app-server 直接取得桌面 `read_thread` 的受支持契约，不应通过复用桌面身份凭据解决。

### 方向二：通过官方扩展接口增加 RCM 只读适配工具

这是技术可行性方向，尚未实施，也不冒充 `codex_app.read_thread`。

拟议调用关系：

```text
网页选择会话 B
  → 原生会话 A 收到引用标识
  → 模型调用 rcm_read_referenced_thread
  → RCM 校验发起会话、轮次和引用范围
  → 目标机器的原生 thread/read + thread/turns/list
  → 原生工具结果回到同一轮次
```

新网页会话可在 `thread/start` 声明动态工具。工具处理器只能转发已核实的原生只读接口；不运行新模型循环，不恢复或接管 B，不改写历史、不生成摘要替代原文。原始分页游标和消息保持原生语义，工具输出设定明确的有界读取范围。

仍需解决：

- 当前 `Manager.onRequest` 将客户端工具存为待处理请求，默认只允许取消。必须增加后台处理器，不能把执行依赖于浏览器标签页。
- 引用权限按目标连接、发起 threadId、轮次与允许引用的 ID 校验；不允许模型自行指定任意主机或文件路径。只读不等于跨账号可读。
- 同一请求去重；断连、进程重启、过期轮次和读取失败必须返回真实失败，不伪造成功。
- 旧网页会话没有动态工具注册参数，不能直接承诺原地补齐。也不能默认 fork 后当作原会话。
- 新会话以后交给桌面或其他客户端时，动态工具声明可能仍存在，需要验证处理器缺失时的行为。

[官方 MCP 文档](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)另提供标准工具接入机制，可研究由引擎管理只读 MCP 适配器，以减少动态工具对单一客户端的依赖。是否能通过本版本的会话配置覆盖给旧会话启用、恢复时是否生效及跨入口兼容均未验证；不修改全局配置进行推测性修复。

项目 [AGENTS.md](../AGENTS.md) 要求原生接口不可用、未开放或未验证时，不得用自建执行逻辑补齐。因此方向二只能作为显式的产品扩展选项：其底层读取走原生接口，但模型工具由 RCM 提供，不能当作桌面原生能力已经支持。实施前需明确是否接受这一边界；本次调研不自动采用。

## 建议推进顺序

1. 若需求是“网页创建的会话被 @”：沿用现有实现，待部署条件满足上线，不增加新执行通道。
2. 若需求扩大到“完全不依赖桌面，所有网页会话互相 @”：先明确是否接受 RCM 自有只读工具，再做独立验证。优先验证新会话闭环，同时把旧会话和交还桌面兼容性列为独立验收条件。
3. 端到端验收必须包含原生工具调用事件与隐藏随机标记匹配，以及只读无接管、同名身份、分页、连接隔离、断连恢复和旧会话能力边界。
