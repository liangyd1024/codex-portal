### 定位步骤与结果

另取桌面各一次 CPU profile，按采样节点自己的 URL 归类，应用自身采样约基准 57.12 ms、候选 82.49 ms；扩展约 124.15／100.10 ms。候选包含 React 执行与订阅成本，但样本分散，尚不足以确定一个占主导的组件。没有关闭扩展、替换 React 或删减界面。

首先在隔离夹具中将首次模拟 SSE 打开固定在 CSRF 响应前，再运行 16 个同序样本。额外读取仍出现：桌面基准 16／20／20／20，手机基准 20／16／16／20，候选两类设备均 20。因此“仅由首次 SSE 打开时机造成”这一假设未成立，该轮不作为等请求量性能验收。

随后加入只读事件时间线，桌面和手机各取新旧一个样本，不阻止任何浏览器事件，不替换应用处理器。观察到：

- 桌面基准的普通 `pageshow` 先于 `rcm-ready`，只有一次状态读取，共 16 个请求。
- 桌面候选的普通 `pageshow` 在初始化读取后到达，约 0.2 ms 后出现第二次状态读取，共 20 个请求。
- 手机两版均在初始化读取后收到普通 `pageshow`，随后出现第二次状态读取，均为 20 个请求。
- 时间线中的 `pageshow.persisted` 都为 false。状态请求调用栈与源码中的 `installThreadSync → resumeWorkspace → loadStatus` 相符；该共同恢复路径会继续读取当前会话和侧栏。

诊断夹具位于 `test/fixtures/startup-order-browser.js`，只在隔离入口注入；语法检查及上述浏览器运行通过。它固定早期 SSE 顺序并记录事件，不保证所有启动事件顺序一致。原始 CPU、请求和事件记录保存于仓库外。

本轮证据将一个具体重复工作机会定位到首次普通 `pageshow` 的恢复刷新，而非认定候选独有功能回归。后续如合并该重复读取，必须保留 BFCache 返回、真实焦点／可见性恢复、启动失败重试及断线恢复，且重新检查请求数量与状态新鲜度。当前没有修改这项产品行为；整体性能门槛仍未通过。
