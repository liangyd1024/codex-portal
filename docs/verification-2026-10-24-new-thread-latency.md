# 新建会话耗时排查与发送解锁

## 真实服务采样

仅操作专用测试会话，输入要求只回复 OK，不读取文件或调用工具。

- 浏览器从提交开始：创建 HTTP 5336ms，发送 HTTP 98ms，发送后的详情 HTTP 1302ms。原生用户消息约 21.6 秒到达，首段助手文本约 31.0 秒到达。
- 独立 RCM 诊断连接逐段测量：账号预检 3ms，引用工具准备 61ms，原生 thread/start 5231ms，turn/start 10ms。首轮完成耗时约 21.1 秒（从发送开始）。
- 同期原生服务日志反复出现 `failed to refresh available models: request timed out`；model/list 单次 5055ms。创建慢点位于原生调用，模型目录刷新超时是高度相关线索，尚未通过网络修复对照实验确认全部因果。
- 原生工具启动事件包括 codex_apps、cua_repl、node_repl 和 rcm_references。引用工具较早 ready，codex_apps 最后 ready。首轮存在工具初始化等待；未禁用任何工具，不能将总延迟全部归因于单一工具。
- 本次没有修改 Codex 安装、全局配置、原生数据库或重启引擎，没有中断既有任务。

## 网页优化

原生发送成功后，立即释放发送锁。详情继续异步同步，复用现有请求合并和迟到响应保护。原来详情读取完成前保持发送锁，真实样本额外阻塞约 1.3 秒；修改不缩短原生创建或模型首字时间。

保留原生发送结果、发送回执、失败草稿和请求去重。详情同步失败按既有方式报告，不重发消息。未增加轮询、请求、缓存或原生业务副本。

原生流程依据：[Codex App Server](https://learn.chatgpt.com/docs/app-server) 的 thread/start、turn/start 和事件流说明。原生 turn/start 返回初始轮次后，客户端继续接收事件，无需等待完整历史才结束提交状态。
