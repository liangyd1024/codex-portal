# 阻塞目标状态与恢复入口

## 原因与范围

真实原生只读核对发现：目标状态为 `blocked`，会话为 `idle`，没有后台命令或排队输入。原生历史显示助手此前因缺少信息标记阻塞，后续普通轮次没有恢复目标。左侧停止运行提示符合实际状态。

RCM 输入框只映射 active、paused、complete，将 blocked 错误显示为“目标待确认”。继续入口只对 paused 显示。本次增加“目标已阻塞”并允许从阻塞状态点击“继续目标”。继续沿用原生 `thread/goal/set`，仅传 status=active 和 user origin，不重建目标、不修改预算、不额外启动轮次。原生设置 active 会启动执行的依据见 [原生目标验收](verification-2026-10-20-inline-goal.md)。

同时明确显示 budgetLimited 和 usageLimited。未为这些状态新增恢复操作，未更改原生限制。普通消息不自动恢复目标。未知或读取失败仍显示“目标待确认”。未修改原业务会话的目标状态。

- ego-browser 独立 4327 预览、全新状态目录。桌面菜单、阻塞/暂停/预算/用量状态、恢复成功、失败保留草稿、请求挂起时保留阻塞状态、读取错误隐藏恢复操作、断连禁用工具均通过。键盘 ArrowDown 导航与 Escape 焦点恢复通过。

- 恢复只产生一次目标 POST，无普通消息 POST；成功和失败均保留草稿，无浏览器脚本错误。没有新增网络请求或轮询；状态映射仅常量查找。未做 CPU、内存基准，不声称性能最优。
- 未触发真实模型目标恢复，未操作原业务目标；真实恢复执行全链路未重测。未做实体手机、真实中文输入法及系统剪贴板验证。本次未修改输入事件。
