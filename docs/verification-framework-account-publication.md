# 账号显示重复发布优化

对照正式 `227dbfe`。在候选 `dc4bba1` 启动采样中，账号显示发布触发八次 React 提交。原显示层每次收到新对象都会更新 store，即使隐藏状态、文字、提示和可访问标签均未变化。

本次只调整 AccountUsage 的显示发布：逐项比较 hidden、text、title、ariaLabel；保持未变化标签的对象引用，两组标签均不变时不更新 store。字段使用严格相等，保留 undefined 与空字符串的区别。新状态仍同步提交。账号读取服务、缓存间隔、强制刷新、上下文检查和迟到响应规则未变。

## 验证

类型检查、构建、完整 873 项 Node 与 74 项 Python 回归通过。ego-lite 使用桌面 1480×747、DPR 2，以及 iPhone 12 模式 390×844、844×390、390×480、DPR 3、触控。所有业务数据和写操作来自隔离夹具。

正常账号、API Key、额度边界、登录失效、未登录和读取失败共 48 样本、24 对状态完全一致。比较两个账号控件的文字、title、可访问标签、隐藏属性、矩形、字体、颜色、背景、边框、间距和轮廓；可见用量按钮的详情提示也一致。无页面异常和横向溢出。

账号切换追加四种视口、八条流程，每条十一种状态，共 44 对状态一致。覆盖挂起旧读取、切换 API Key、释放旧成功响应、读取失败及恢复、挂起失败响应后切换成功账号、释放旧失败响应、额度边界和未登录。比较文案及隐藏属性、读取次数、实际视口；两个账号 DOM 节点始终复用，无异常或溢出。

## 定位方法

提交计数通过临时包装 React 调试钩子获得，原回调完整执行并保持 this 和参数，采集完成后恢复。第一轮默认堆栈深度不足以显示应用调用者；第二轮只在读取堆栈时临时增加深度，并立即恢复。记录仅用于定位和计数，不能用于耗时比较。正式产品不包含这些诊断代码。

优化后桌面和 iPhone 竖屏的账号发布提交均由 8 次降为 5 次。对应总提交分别由 92 降为 89、由 87 降为 84。此计数只证明该启动样本减少三次提交；不能据此宣称整个应用已提速。当前模型选项等其他发布仍有提交开销，整体性能门槛继续保留。

## 无诊断包装的耗时复测

正常扩展环境下，对照优化前候选与本次候选，桌面和 iPhone 竖屏各按旧／新／新／旧加载，共八次。两边使用相同虚构会话。

| 设备／候选 | ScriptDuration 两次读数 ms | TaskDuration 两次读数 ms |
| --- | --- | --- |
| 桌面优化前 | 96.11／103.12 | 496.85／596.23 |
| 桌面优化后 | 99.63／105.22 | 752.71／630.25 |
| 手机优化前 | 107.95／105.31 | 658.37／620.10 |
| 手机优化后 | 106.03／107.30 | 669.51／636.79 |

无页面异常。上述少量样本没有证明稳定的耗时改善；文档 CPU 计数仍包含工具、扩展及缓存条件影响，不能用它归因账号组件。此次只确认减少了三次无变化提交，未解决整个首屏的性能差异。
