# RCM 页面性能与源码分层排查

日期：2026-10-22。范围：保持现有功能，排查加载、同步、渲染、远程读取与源码分层，给出修复计划。本次只新增排查文档和测量数据，没有修改功能代码，没有部署或重启服务。

结论：有明确的优化空间。优先处理重复侧栏请求、侧栏对桌面状态探测的等待，以及长会话流式更新的全量计算。现有项目已有模块化基础，适合继续采用原生 JavaScript 和 Node.js 的模块化单体结构，按职责逐步拆分。

## 测量范围与口径

- 正式网页：`http://127.0.0.1:4317`，采样版本 `8c414c8be53f66013fd13e3845bcbc426a7b5647`。
- 浏览器：ego-browser；桌面视口 1440×900，窄屏视口 390×844；未限速，未降低 CPU 速度。
- 初次观察后，桌面连续重载 3 次，窄屏重载 1 次。未清理浏览器缓存或用户存储。因此不把首次观察称为严格的冷缓存测试。
- 长会话使用正式版本的前端资源，在独立的 `localhost` origin 注入仓库已有的浏览器 fixture。所有 `/api/` fetch 和 EventSource 都被替换为模拟实现。资源记录确认模拟测试没有发出真实 API 请求。
- 模拟每轮含用户消息、含列表和加粗的助手正文、命令输出。按 5、50、200 轮加载；每组追加 10 次少量文字，测量现有 80ms 批处理回调的执行时间和创建元素数。时间不包含等待批处理的 80ms，也不等于完整输入延迟或 INP。
- 50、200 轮代表已持续使用或加载过更早历史的场景。真实首个历史页通常为 5 轮，不能把 200 轮结果当作每次打开会话的表现。
- Python 使用项目现有只读适配器做一次 cProfile 采样。该次未提供账号布局参数，仅用于定位耗时，不作为账号布局验证。
- SSH 通过现有连接配置和原有严格主机校验路径，分别测量只读接口及仅返回空 JSON 的 Python 调用。没有停止目标服务或发送真实会话消息。
- 采样期间其他会话继续工作。仓库从初始版本推进到 `e063870`；性能结论使用上述已安装版本，结构问题同时核对了工作区源码。其他会话的修改未被本次提交包含。

这是一组本机诊断样本，不是线上分位数统计。未进行实体手机、iOS Safari、限速弱网、多客户端压力、长时间内存泄漏测试，也未测试全部真实消息生命周期。此次未修改行为，没有运行 `npm test` 或新增预览服务。

## 实测结果

### 正式页面加载

| 样本 | 首次内容绘制 FCP | 框架就绪 `rcm-ready` | 首批侧栏 DOM 出现 | 完成的侧栏请求 | 状态请求 |
| --- | ---: | ---: | ---: | --- | ---: |
| 桌面 1 | 80ms | 119ms | 2878ms | 1365ms、2717ms | 3 |
| 桌面 2 | 88ms | 123ms | 2920ms | 1351ms、2727ms | 3 |
| 桌面 3 | 72ms | 114ms | 2846ms | 1344ms、2682ms | 3 |
| 390px 窄屏 | 72ms | 120ms | 4228ms | 1345ms、2692ms、1425ms | 3 |

`rcm-ready` 表示框架事件已绑定，不代表模型、项目、侧栏和会话数据全部就绪。窄屏侧栏默认收起，表中记录的是数据节点创建时间，不是抽屉打开时间。窄屏只有一个样本，4.23 秒仍需复测，不作为稳定均值。

这几次首页样本未观察到超过 50ms 的主线程长任务。桌面和窄屏均未发现页面横向溢出。首页的主要等待发生在数据链路。

每次都传输了 42 个 JS/CSS 资源，原始响应体合计 440,929 字节，约 441 KB。资源未压缩，没有零传输的缓存命中。正式静态响应为 `Cache-Control: no-cache`，没有 `ETag`、`Last-Modified` 或 `Content-Encoding`；携带 `If-Modified-Since` 的探测仍返回 200。

对同一组资源逐文件离线压缩：gzip 合计 137,483 字节，Brotli 合计 113,823 字节，分别减少约 69% 和 74%。这是响应体体积估算，尚未接入服务，不代表页面已提速相同比例。

### 侧栏与 SSH

| 测量项 | 结果 | 说明 |
| --- | ---: | --- |
| 本机 `read_sidebar` | 1294ms | 单独只读 profile，82 个未归档会话、39 个项目 |
| 其中 `sidebar_activity` | 1222ms | 约占该次总耗时的 94% |
| 其中 socket `recv` | 1202ms | 等待桌面运行状态快照 |
| SSH `/api/sidebar` | 5526ms | 一次真实只读样本 |
| SSH `/api/projects` | 4851ms | 一次真实只读样本 |
| 本机空 Python 读取 | 37ms | 不读取业务数据 |
| SSH 空 Python 读取 | 4683ms | 不读取业务数据，含连接、认证和进程启动等成本 |

SSH 空读取已接近项目列表耗时，说明连接与进程调用成本值得优先调查。它不能进一步证明 DNS、网络往返、认证或远端启动分别占多少时间。

### 模拟流式渲染

| 已加载历史 | 视口 | 单次更新中位数 | 最小～最大 | 每次创建元素 | 正文元素总数 |
| --- | --- | ---: | --- | ---: | ---: |
| 5 轮 | 桌面 | 6.6ms | 5.1～14.7ms | 688 | 581 |
| 50 轮 | 桌面 | 34.8ms | 30.5～39.6ms | 6628 | 5801 |
| 200 轮 | 桌面 | 127.8ms | 119.7～137.4ms | 26428 | 23201 |
| 50 轮 | 390px | 80.0ms | 77.2～84.2ms | 6628 | 5801 |

200 轮桌面和 50 轮窄屏均复现长任务。浏览器长任务阈值为占用主线程 50ms 或更久，可能影响输入、滚动和事件响应。[MDN：PerformanceLongTaskTiming](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongTaskTiming)

元素数包括生成后用于比较的临时节点，因此可大于最终挂载节点数。计时含少量诊断包装开销。CPU 采样同时观察到 `reconcileMessages`、`reconcileNode`、节点追加、垃圾回收和输入框镜像渲染的消耗；没有把采样命中数直接换算成精确耗时占比。

## 已确认的问题与修复意见

### 1. 首屏重复读取，较早结果被作废：优先级高

源码：[`public/app.js`](../public/app.js) 的 `init`、`setupEvents`、`resumeWorkspace`、`refreshWorkspace`、`loadStatus`、`loadThreads`。

初始化读取状态后刷新工作区；SSE 首次打开又调用恢复刷新；首次 `manager/status` 还可能触发工作区刷新。这些入口只做了局部合并。`loadThreads` 对非追加请求没有相同参数的在途合并，每次都递增 `listVersion`。

实测两次侧栏请求几乎同时开始，较早请求约 1.35 秒完成，却因版本已变化而不应用。页面直到后一个请求完成才显示侧栏。版本检查本身是必要的，问题是相同上下文也发出了重复请求。

修复建议：

1. 将首次 SSE 建立与断线恢复分开处理，首屏由单一入口安排必要读取。
2. 按连接实例、账号上下文、搜索词、归档状态、分页游标和选择上下文合并相同只读请求。
3. 在读取期间收到变更通知时标记需要再读一次，避免丢掉新变化。
4. 上下文变化时保留迟到结果保护。取消只读请求时同时考虑服务端正在进行的工作。
5. 状态读取可复用同一次启动读取结果，不重复阻塞刷新链路。

验收：一次正常首屏只发起一轮相同参数的侧栏读取；变更事件、搜索切换和账号切换仍可获得正确的新结果。不能用删除版本检查换取速度。

### 2. 侧栏内容等待桌面运行状态：优先级高

源码：[`lib/sidebar.mjs`](../lib/sidebar.mjs) 的 `readSidebar`；[`scripts/passive-store.py`](../scripts/passive-store.py) 的 `read_sidebar`、`sidebar_activity`、`desktop_activity`。

侧栏先读取账号和原生列表，然后同步等待桌面实时状态观察。`desktop_activity` 的总期限为 1.2 秒；部分候选会话没有桌面所有者返回快照时会等到期限。当前采样中这一步占比约 94%。

修复建议：先返回已经核实的项目、分组与会话数据，将桌面活动状态作为独立的异步刷新。保留现有状态来源、有效时间和连接版本核对。首次尚无可靠状态时显示未知，获得真实快照后更新；不能把历史 `inProgress` 当作当前运行证明。

第一步可先做请求合并，不改变接口。随后拆分可选状态观察，评估同一目标的并发观察合并。写操作前的忙闲检查仍须读取当前原生状态。

验收：人为延迟或阻断桌面状态快照时，项目与会话列表仍能出现；运行标记在有效快照到达后更新，断开或过期时撤去。新旧账号结果不得混用。

### 3. 已有 DOM 复用，但正文变化仍重算全部历史：优先级高

源码：[`public/app.js`](../public/app.js) 的 `renderMessages`、`renderItem`、`scheduleStreamRender`；[`public/message-dom.js`](../public/message-dom.js)；[`public/message-body.js`](../public/message-body.js)。

当前并非每次清空已挂载正文。已有 keyed DOM 协调，能保留许多历史节点。剩余成本在于：每次助手文本变化都对所有轮次生成整体 JSON 签名，再遍历全部轮次、解析 Markdown、生成新树，最后递归比较。旧节点保留下来，构建与比较的工作仍然发生。

修复建议：

1. 以连接、会话、轮次和消息 ID 管理渲染记录，分别记录文本、状态、工具输出和显示上下文的变化。
2. 只重新解析发生变化的消息。已结束且内容未变的消息直接复用渲染结果。
3. 保留当前流式批处理，再按变化类别更新正文、控制按钮、状态和文件列表。
4. 对最新消息内部可先保留完整 Markdown 重解析，优先消除整个历史的重复工作。
5. 缓存键要包含影响显示的状态和链接上下文；会话切换、清除缓存与连接变化时正确失效，并限制缓存大小。

验收：单条消息追加时，未变化历史不再按轮数重新创建节点；原始文字、代码、表格、文件、图片、耗时和过程分组不变；展开状态、焦点、文本选择及加载更早记录时的滚动位置不丢失。

不以截断回复或删减历史减少开销。大规模虚拟列表暂列后续评估，因为它会影响页面查找、复制、滚动锚点和无障碍访问。

### 4. 静态资源每次完整传输：优先级高，实施风险较低

源码：[`server.mjs`](../server.mjs) 的静态文件响应；[`public/bootstrap.js`](../public/bootstrap.js) 与 [`public/index.html`](../public/index.html)。

当前对较大的 JSON 已支持 gzip，但 JS/CSS 静态分支没有压缩，也没有条件请求校验器。`no-cache` 允许保存响应，但复用前需要向服务器验证；它本身不等于完全禁止缓存。[MDN：Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

修复建议：

- 在静态响应中增加 ETag 与 304；保留 HTML 的更新检查。
- 按 `Accept-Encoding` 提供 gzip，必要时增加 Brotli；设置正确的 `Vary` 与响应元数据。
- 不在每个请求内重新进行高等级压缩。可按 release 缓存压缩结果，或在发布产物准备阶段生成。
- 若以后使用长期缓存，必须给整张模块依赖图稳定版本化，不能只给入口加版本参数。
- 把首屏确实需要的样式提前到 HTML；对主入口和少量关键模块评估 `modulepreload`，减少 `bootstrap → app → 依赖` 的发现等待。预加载需要控制范围。[MDN：modulepreload](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/modulepreload)

验收：重复访问未变资源返回 304 或正确命中版本化缓存；部署后能获得新资源；配对前后的资源权限保持一致；SSE 持续及时送达；API 业务响应继续遵守现有缓存边界。

### 5. SSH 读取重复承担连接成本：优先级高，需单独验证方案

源码：[`lib/ssh.mjs`](../lib/ssh.mjs) 的 `sshArgs`、`remotePython`；[`lib/local.mjs`](../lib/local.mjs)；[`lib/manager.mjs`](../lib/manager.mjs) 的 `serviceAction`、`passive`、`detail`。

每次只读 Python 调用都会启动新进程。SSH 参数明确使用 `-S none` 和 `ControlMaster=no`，不复用已有 SSH 控制连接。WebSocket 隧道长期存在，但这些 Python 读取没有借助它复用 SSH 会话。

初次选中会话时先获取预览，再获取完整详情；详情内又分别读取元数据和历史。这种渐进显示有价值，但也可能重复承担远程启动与读取成本。真实长会话详情尚未采样，具体收益需补测。

修复建议依次为：

1. 合并相同的在途只读查询；确认侧栏返回的项目字段能否满足对应项目视图，避免无必要的重复 `/api/projects`。
2. 对同一快照所需的只读数据评估一次 Python 调用完成，保持原生历史分页与输出增量协议。
3. 调查 SSH 连接阶段耗时，并验证由 RCM 独占、按目标身份隔离的连接复用方案。继续保留主机校验、身份验证和普通断开语义。
4. 已核验的原生读取接口可以优先使用；未核验的接口不能为了加速直接替换现有行为。

不新增业务执行引擎或任务调度器，不重启在用原生服务。连接复用需要验证重连、目标切换和多入口场景后再实施，不能仅凭这次单样本直接上线。

### 6. 隐藏区域与无关区域仍有刷新：优先级中

源码：[`public/app.js`](../public/app.js) 的 `init`、`setAutoRefresh`、`scheduleStreamRender`、`renderSession`、`renderFiles`、`renderControls`；[`public/inline-mentions.js`](../public/inline-mentions.js)；[`public/sidebar.js`](../public/sidebar.js)。

- 80ms 的流式回调同时刷新正文、会话状态、文件列表和输入控制区。`renderFiles` 每次遍历全部已加载工具项。
- 输入框镜像在控制区渲染时读取计算样式、宽高并重新绘制，助手正文增加不一定需要这些操作。
- 每 5 秒刷新控制区与侧栏的计时器没有可见性条件；每 30 秒的项目/模型自动刷新也没有统一的后台暂停判断。部分其他轮询已经正确检查可见性。
- 侧栏用整体签名跳过未变化结果；签名变化时会重建整棵侧栏树，折叠分组下的子节点也全部创建。
- 首屏初始化手机访问和更新面板，即使详情栏关闭，也会读取相关数据。手机地址二维码随后下载。

修复建议：建立统一的页面刷新生命周期；只重绘有变化的区域；将隐藏设置面板的初始化延后到首次使用；对折叠分组评估首次展开时创建节点。运行通知、待回答提示、重连和草稿保存保持原有语义，不能直接暂停全部 SSE 事件。

验收：切到后台后减少非必要读取与渲染；返回前台立即同步；真实运行状态和重要提醒仍正常；首次打开延迟加载面板有进行中、失败和重试反馈。

### 7. 随数据量增长的开销：优先级中到低，先补测

- `read_sidebar` 读取所有符合来源条件的会话和已读记录，再在 Python 处理归档、搜索、分组与排序。归档列表分页返回，普通会话列表全量返回。现有样本中它不是主要等待项，但历史增大后需重新量化。
- `desktop_membership` 与 `read_sidebar` 重复读取全局状态、项目及根目录，单次读取内可以复用已经取得的数据。
- 详情恢复缓存已限制为 4 个会话并按 5 秒合并写入，但大型快照仍需计算整体签名及结构化复制。可评估按变更版本判断，避免签名遍历。
- `selectThread` 等待 IndexedDB 恢复后才启动网络刷新。可以评估并行竞速，但必须保留网络新结果优先的版本保护。
- Node 侧状态落盘使用同步文件写入；远程结果使用同步解压与 JSON 解析。这些是潜在事件循环阻塞点，目前未证明它们是主要瓶颈。

上述项目先补充数据量与持续运行采样，再决定是否修改。原生数据库保持只读，不通过增加索引、修改表或改写原生记录优化。

## 已有设计应继续保留

- 原生 ES Modules，无前端框架和额外运行时依赖。
- 独立启动失败恢复，不依赖主模块成功加载。
- 会话详情请求去重、选择版本与连接版本校验。
- SSE 批处理、断线恢复、可见性控制下的会话历史补偿同步。
- 按轮次分页的历史读取，原生读取回退及游标类型隔离。
- 按消息和轮次 ID 协调 DOM；图片、代码与展开状态保护。
- 命令输出增量、压缩及 65536 字符显示窗口，完整输出仍保留。
- IndexedDB 恢复快照及数量限制。
- 已有 Node 与 Python 行为回归测试。

优化应在这些基础上减少重复工作，不更改 Codex 的会话或执行语义。

```text
├── config/              示例配置；真实配置在仓库外
└── docs/                能力研究、验收与部署记录
```

运行链路为：浏览器 `public` → HTTP/JSON、SSE → `server.mjs` → `lib` 能力适配 → WebSocket RPC、桌面 IPC、本机/SSH 读取器 → Codex 原生服务或只读数据。

这是一个有功能模块划分的轻量单体项目。前后端源码有区分，但由同一个 Node 服务提供。前端直接运行原生模块，没有独立打包步骤。目录不叫 `src/` 并不构成问题；目前需要改进的是职责和依赖边界。

主要集中点，以采样版本为准：

| 文件 | 大小与行数 | 职责问题 |
| --- | --- | --- |
| `public/app.js` | 123 KB，1518 行 | 同时持有请求、状态、渲染、操作和生命周期 |
| `lib/manager.mjs` | 49 KB，712 行 | 连接编排与多个功能、持久化职责集中 |
| `server.mjs` | 23 KB，198 行 | 代码行较长，HTTP 边界和功能路由混合 |
| `scripts/passive-store.py` | 48 KB，896 行 | 侧栏、历史、活动、图片和输出读取集中 |
| `public/styles.css` | 84 KB，521 行 | 全局和功能样式集中，与其他 CSS 覆盖关系需追踪 |

检查到的依赖问题：

- `lib/manager.mjs` 直接导入 `public/questions.js` 与 `public/connection-state.js`。共享纯逻辑有复用价值，但存放在浏览器目录会使依赖方向不清晰。
- 4 组双向依赖：`manager ↔ composer`、`manager ↔ history-read`、`manager ↔ message-input`、`ssh ↔ file-transfer`。
- 前三组与从 Manager 导出通用 `AppError` 等定义有关；后一组是 SSH 参数和文件传输工厂相互引用。
- 这些 ES Module 循环目前可运行，没有据此判定线上故障。但会增加独立初始化、测试隔离和后续模块调整的难度。
- 部分测试从大文件截取函数文本到 VM 中运行，说明功能入口还不够容易单独导入测试。
- 当前没有统一的前端构建、lint 或目录依赖约束。发布通过导出 Git 版本并启动 Node 服务完成。对现有技术栈而言，打包工具不是本次性能修复的前置条件。

## 建议的分层方式

保留根目录布局，在现有目录内逐步按职责拆分。先建立模块边界，再按需要移动文件。推荐方向：

```text
server.mjs                 只负责服务组装与启动
public/
  app.js                   浏览器组装入口
  core/                    API、SSE、页面状态和刷新生命周期
  features/
    conversation/          会话加载、消息渲染、历史与滚动
    sidebar/               分组、列表、菜单和原生操作入口
    composer/              草稿、模型、技能、发送和输入交互
    automations/           原生任务展示与会话跳转
    settings/              手机、更新、浏览器备份
  ui/                      公共按钮、图标、提示、弹窗
  styles/                  基础变量、布局、功能样式和移动覆盖
lib/
  core/                    通用错误、连接上下文和基础约定
  http/                    路由、认证、响应、静态资源和 SSE
  services/                会话、侧栏、目录、任务等原生能力适配
  transports/              RPC、IPC、本机与 SSH
  persistence/             RCM 自有配置、展示缓存和恢复状态
shared/                    前后端共享的纯数据转换与协议形状
scripts/                   保留原有入口；读取与维护逻辑逐步拆分
test/                      按对应功能分组
```

依赖方向：页面交互调用页面状态和 API；HTTP 路由调用能力适配；能力适配调用传输和 RCM 持久化；通用错误与共享数据模块不反向依赖功能模块。Codex 原生服务继续决定任务与会话状态。

第一批可先抽出通用错误与 SSH 参数，解除明确的循环依赖；再将真正跨端的纯函数放入 `shared`。浏览器访问共享文件仍需显式静态资源白名单，不能直接暴露仓库目录。移动前端或 Python 模块时，需要同步核对相对导入、静态映射、脚本打包与 release 安装路径。

目录拆分本身不保证更快。只有它帮助实现按需加载、独立更新和减少重复读取，才会产生运行时收益。也不需要把所有文件立即搬到新目录。

## 分阶段计划

以下是工作量估算，不是交付日期承诺。每批独立验证、串行提交。功能修改获准进入实施后，按项目既有流程提交到 master、推送并部署；忙闲检查不通过时记录阻塞，不中断其他任务。

| 批次 | 工作 | 粗略工作量 | 主要验收 |
| --- | --- | --- | --- |
| 1 | 统一首屏读取；侧栏和状态请求合并；静态 gzip 与条件缓存 | 1～2 人日 | 同参数首屏侧栏 1 次；资源响应体约 140 KB 量级；更新后资源正确 |
| 2 | 侧栏内容与桌面活动异步刷新；隐藏设置按需加载；页面刷新生命周期统一 | 1～2 人日 | 桌面活动延迟不阻塞列表；前后台恢复和通知无回归 |
| 3 | 消息级增量渲染；文件列表、状态区和输入镜像按变化更新 | 2～3 人日 | 未变历史不重建；50/200 轮追加成本显著降低；保留完整内容和交互 |
| 4 | SSH 分阶段计时、只读调用合并、连接复用验证 | 1～2 人日调查，实施另估 | 降低每次刷新中新建连接数量；连接、身份校验和断开语义正确 |
| 5 | 抽出共享纯逻辑与通用错误；解除循环；逐步缩小 app/manager | 1～2 人日，随功能批次推进 | 直接导入测试；依赖方向明确；现有 API 和界面行为一致 |

建议目标，仅用于后续验收，不代表已实现：

- 第一批后，本机首屏不再因重复请求等待约两倍侧栏读取时间；以单次侧栏耗时作为对照。
- 第二批后，在本次相似数据规模下，本机列表内容争取在 0.5 秒内出现，桌面活动状态随后补齐。需补足账号读取和真实运行场景样本后确认。
- 第三批后，同一 fixture 的 200 轮单条追加争取控制到 50ms 以下，50 轮常见更新进一步接近一帧预算。先确保创建节点数不再随未变历史线性增长，再评估绝对时间。
- SSH 优先验证连接复用和批量只读的实际收益，不承诺在网络未知时达到固定毫秒数。

验证时保持功能不变：原文逐项对比；会话与连接切换的迟到响应；SSE 重连；草稿与中文输入法；通知与待回答；模型、技能与附件；焦点、图片、代码复制、过程展开；加载更早历史和滚动跟随；本机与 SSH；桌面和 390px；部署前后缓存版本。性能计数可做回归测试，绝对时间应保留机器与样本说明，避免脆弱的固定时间断言。

每批行为修改先跑相关测试，交付前跑 `npm test`。UI 验收使用 ego-browser。真实服务和 fixture 结果分别记录；涉及输入流程时补测中文输入法，手机体验最终需要实体设备验收。
