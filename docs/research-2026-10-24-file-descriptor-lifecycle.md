# 文件句柄驻留与泄漏排查

排查代码基线：`f97e7cf`。原生版本：`0.163.0-alpha.11.1`。本次只调查和提供方案，不修改生产逻辑，不重启现有网页、桌面或专用引擎。

## 结论

在本次重复创建、退订、网络断开和命令执行测试中，没有复现不可回收的句柄泄漏。不能据此排除长期运行、工具故障、异常终止或不同版本的泄漏。

已确认原服务的容量问题：专用引擎直接创建的工具进程继承了 256 的软限制；已加载会话、常驻工具和后台命令接近该限制。已完成的启动额度修复见 [额度验收记录](verification-2026-10-24-engine-file-limits.md)。当前运行的引擎尚未通过维护重启应用新额度。

网页端存在长期保留订阅带来的资源驻留。桌面端也保留相同类型的工具进程和管道；问题不是网络请求独有。没有证据表明每次网页 HTTP 请求或每次读取技能文件都会永久增加句柄。

## 真实进程快照

以下为同一轮只读观测。进程实时变化，数字不代表固定上限或所有时刻。

| 项目 | 网页专用原生引擎 | 桌面主原生引擎 |
| --- | ---: | ---: |
| 数字文件描述符 | 240 | 151 |
| 管道 | 145 | 111 |
| 普通文件 | 67 | 24 |
| 其余类型 | 28 | 16 |
| 直接子进程 | 52 | 37 |
| 打开的会话记录 | 12 | 7 |

网页引擎的 67 个普通文件包括 12 个会话记录、14 个锁文件、39 个 SQLite 数据库及 WAL/SHM 句柄、2 个服务日志。没有发现技能 Markdown 文件大量保持打开。数据库存在多个连接及伴随文件，不能仅凭同名文件重复打开就认定泄漏。

网页专用引擎有 18 个 `node_repl`、18 个 `cua-repl`，以及会话引用 MCP、工具宿主、开发预览及测试命令等进程。桌面主引擎有 17 个 `node_repl`、8 个 `cua-repl`，另有其他 Node 服务及工具宿主。普通文件以外的管道是引擎与子进程通信所需的描述符。

原生只读接口返回网页引擎有 18 个已加载会话，其中 12 个持久会话、6 个临时会话。快照时 3 个 active、15 个 idle。部分持久会话的最近更新时间距观测约 10 至 38 小时；这不是精确的连续空闲时长。

RCM 记录 23 个期望订阅，不等于原生当前加载数。部分临时会话未出现在当前入口的订阅记录中，不能据此认定没有其他订阅或是孤儿会话。本次未改变这些会话。

另一个 active 开发会话保留了多条预览、测试及查询后台命令，原生 `thread/backgroundTerminals/list` 可读取。不能把正在执行的其他会话任务当成泄漏直接终止。

## 可重复的回收实验

使用配置中的相同原生二进制，启动独立临时测试引擎。工作目录独立，设置 `thread_unload_delay_secs=5`，使用专用临时会话。没有借用、退订或停止已有业务会话。只停止本次测试创建且已完成任务的独立引擎。

### 原生协议，三轮

| 阶段 | 工具子进程 | 管道句柄 | 已加载会话 |
| --- | ---: | ---: | ---: |
| 启动基线 | 0 | 0 | 0 |
| 新建并保持订阅超过 5 秒 | 2 | 6 | 1 |
| 原生退订，等待 7 秒 | 0 | 0 | 0 |

三轮均恢复，普通文件维持 23 个；网络连接短暂波动。测试说明即使未发送消息，新建会话也会启动工具；保持订阅时，卸载延迟不会触发。上述每会话 6 个管道是本机当前工具配置实测，不是所有 Codex 环境的固定值。

### RCM 网络转发，三轮

使用当前 `output-relay.py`、本机转发适配和 `RpcClient`，连接隔离的原生 Unix Socket 引擎。已核对正式采集器脚本与仓库源码一致。

每轮新建临时会话后保持连接 6 秒，出现 2 个子进程和 6 个管道。关闭该测试客户端，等待 7.5 秒后，子进程及管道全部归零，上游 Unix Socket 数回到基线。三轮均没有积累。此实验验证空闲断开，不代表活动任务断线、系统休眠或异常终止全部通过。

### 实际命令任务，两轮

每轮要求在专用临时会话运行简单 Python 输出命令，等待原生 `turn/completed`，再退订并等待卸载。

- 两次轮次状态均为 completed。
- 两次退订后均为 1 个共用 `codex-code-mode-host` 子进程、3 个管道、27 个普通文件，已加载会话为空。
- 第二轮没有在第一轮基础上继续增加。首次执行工具后的共用宿主及连接属于本次可观察到的稳定驻留，未表现为逐轮积累。

另一次独立复核记录了原生命令完成事件：退出码 0、输出 `12345`。退订后同样回到 1 个共用宿主、3 个管道、27 个普通文件，已加载会话为空。

所有临时数据保留在仓库外，不执行批量删除。测试不是数小时或数天的压力测试。

## RCM 为什么更容易触及额度

`lib/manager.mjs` 将已接管会话保存在订阅记录中；连接恢复时逐项调用 `thread/resume`。切换网页中的当前会话不会自动调用 `thread/unsubscribe`。因此，不再显示的空闲会话仍可能保留工具状态。

`lib/thread-handoff.mjs` 通过原生接口检查活动轮次、目标、后台命令和队列，再退订并确认是否卸载。这是当前已具备的安全释放入口。

`scripts/output-relay.py` 在客户端断开但仍有轮次或命令时保留上游连接，继续采集输出。该行为保护任务和原始输出，但同一连接的其他会话也可能继续保持订阅。待跟踪的轮次和命令结束后才关闭上游；空闲断开已实测回收正常。异常事件遗漏时是否可能滞留，尚未完成故障注入验证。

18 个加载会话的两类常驻工具，按隔离实验估算已可解释约 108 个管道；其余由会话引用工具、共用宿主、后台命令等组成。该数字是基于实验的归因估算，不是逐个管道端点匹配结果。

## 建议修复方案

1. 应用已提交的 4096 启动额度。只在另获授权、完成维护检查后重启专用引擎。该措施增加容量，不作为泄漏已修复的证据。
2. 将“保留会话记录”和“保留运行时订阅”分开。默认历史浏览走只读接口；重新进入交互时再恢复订阅。对离开当前页面且长期空闲的会话，设计按需释放策略。释放前复用现有严格检查，禁止释放运行轮次、活动目标、后台命令、排队输入和待处理请求。
3. 自动释放会失去 REPL 变量及工具连接等临时状态，不能当成纯性能改动直接上线。先明确保留策略和恢复语义；初期可沿用用户主动交还，后续再做可配置空闲期限或容量策略。
4. 调整重连恢复范围，避免仅为阅读历史恢复全部旧订阅。保留任务输出、失败通知和原生目标状态恢复能力；不能通过省略恢复导致消息丢失。
5. 后台预览、测试进程由创建它们的任务在结束时通过原生终端接口收尾。先确认归属和用途，不按进程名称批量结束，也不打断当前 active 会话。
6. 增加退订、重连、重复执行命令、任务失败及工具异常退出的长时间回收验收。固定任务结束后比较会话数、工具进程数和句柄基线；若业务对象已释放而句柄持续单调增长，再按 RCM 转发层或原生层定位最小复现。不得用定期重启掩盖增长。

桌面端只能使用已验证的原生管理能力或正常关闭方式处理。此次没有修改桌面安装、全局配置、数据库或执行逻辑，也没有验证桌面 UI 的具体退订策略及其进程实际软限制。
