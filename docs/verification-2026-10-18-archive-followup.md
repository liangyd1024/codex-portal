# 归档同步继续验收与延迟结果修复

## 新发现

1. 桌面 UI 自动化工具明确拒绝访问 `com.openai.codex`，返回 `Computer Use is not allowed to use the app 'com.openai.codex' for safety reasons.`。这是该工具的安全限制，本项目无法解除；未通过其他 UI 自动化通道绕过。官方会话列表与真实屏幕分别验收。
2. 正式版恢复专用会话“验收手机技能首条消息”时，RPC 超时后首次读取仍未确认，稍晚数据库才变为未归档。上一版只核对一次，漏发恢复通知。补发后 Codex 官方 `list_threads` 出现该 ID，用户也明确回复桌面“已显示”。
3. 该会话随后由桌面进程持有 writer lock，网页版独立引擎 `thread/archive` 返回 `already has an active writer`。只读检查确认目标闲置、无后台任务/队列/活动目标，但写入锁仍在桌面进程。归档未成功，数据库保持未归档，不能记作归档后同步失败，更不能强行隐藏会话。桌面公开于本机的 daemon 并不是持锁的 stdio 进程，不能借连接其他引擎解除此限制。

## 修改

- 将归档/恢复的通知意图保存到连接状态文件旁的 `.archive-sync.json`；写入结果迟到或通知失败时，在之后的侧栏刷新、重连后继续只读核对，确认状态匹配才发送通知。网页进程重启后保留待同步任务。
- 重试只发送通知，不重放归档/恢复请求。按账号隔离、去除重叠刷新通知；新的相反操作不会被旧通知完成回调清除。明确拒绝的请求清除意图。
- 桌面/另一入口持锁时返回 `THREAD_WRITER_CONFLICT` 和可操作的中文提示，要求在持有入口归档；不删除锁、不停止任务、不伪造成功。此限制目前未消除。
- 状态文件只记录本应用的待同步操作，不扩展备份到原生数据库或凭据。

## 验证边界

单元测试覆盖迟到写入、进程重启、通知失败重试、账号切换、并发去重、相反操作竞争、明确拒绝与持锁冲突。正式网页菜单归档被持锁保护拒绝，未按成功记录。用户已确认恢复后的真实桌面显示；后续归档结果另行记录，不能用工具列表代替用户视觉确认。
